# XIUNO XW

基于 [Xiuno BBS 4.1.1](https://bbs.xiuno.com/) 二次开发的分支版本（fork），国产轻量论坛系统。

> 上游 Xiuno BBS 4.1.1 兼容 PHP 8.0 - 8.4，修复了 SMTP 邮件系统，升级了缓存机制（文件缓存 / Redis 认证）。XIUNO XW 在此基础上继续演进。

## 特性

- 轻量：仅 20 多个表，源码压缩后 1M 左右，单次请求处理在 0.01 秒级别
- 响应式：前端 BootStrap 4.5 + jQuery 3.5.1，自适应手机 / 平板 / PC
- 高性能：静态语言编程风格，充分发挥 PHP7+ OPCache 威力；Session + Token 双登录
- 插件机制：hook + overwrite，方便二次开发，不影响性能
- 多语言：自带简中 / 繁中 / 英文 / 俄语 / 泰语
- 强扩展：内置火车头免登录发布接口（loco.php）

**编辑器 · 图片上传前先转 WebP（上传快约 10 倍，编辑帖子不用再干等）：**

- **问题**：`view/js/xiuno.js` 的 `xn.image_resize()` 里是写死的 `filetype = 'png'`（连 JPEG 源也一并转成 PNG），再叠上 base64 的 1.33 倍膨胀 —— 实测一张 1672×940 的图前端要 POST **4711 KB**、1232×706 的要 **2195 KB**。而图片是**从粘贴那一刻就开始异步上传**的：发帖时你在打标题，上传早跑完了，所以"秒发"；编辑时"删图 → 粘贴新图 → 立刻点编辑帖子"，等待就全暴露出来（表现为"要等很长时间"，v1.8.8 之前则是报「内容太长」、要点两次）
- **修复**：新增 `plugin/huux_tinymce/tinymce/upload-prep.js`，**保持原有处理完全不变**（`xn.image_resize` 的限宽 2560 与右下角水印照旧），只把它的结果**再编码成 WebP** 后自己 POST 上传；`init.js` 的 `images_upload_handler` 优先走它。浏览器不支持 WebP 编码、图片解码失败、转完反而更大 → **一律自动回退**到原来的 `xn.upload_file` 流程，行为只会更好不会更差
- **服务端配套**：内容已是 WebP、文件名却还带 `.png/.jpg` 会导致扩展名与内容不一致（静态服务器会按扩展名发出错误的 Content-Type），因此 `plugin/till_thread_locallmage/hook/attach_create_save_before.php` 补了一条：检测到内容是 WebP 就统一改名成 `.webp`（新增 `xw_localimg_is_webp()`，判定 RIFF/WEBP 文件头）
- **实测**：
  - 前端上传正文（真实图）：1672×940 的图 **4711 KB → 433.6 KB**（约 1/10.9），客户端多花 **15ms** ✓
  - 真实 HTTP 上传路由（WebP 内容 + `paste.png` 文件名）：返回 `upload/tmp/1_XXX.webp`、`filetype=image`、`isimage=1`，落盘文件为 `image/webp 1200×675` ✓
  - PNG 常规路径对照：2247 KB 的 base64 仍被服务端优化成 81688 字节的 `.webp`，旧行为未受影响 ✓
  - 全链路冒烟（转 WebP + v1.8.8 的提交守卫一起）：提交 1 次、提交时正文 53 字符、上传正文为 WebP ✓

### v1.8.8 (2026-10-07)

**编辑器（huux_tinymce）· 修复「编辑帖子要点两次，第一次报内容太长」：**

- **原因**：粘贴的图片会先以 base64 内联进正文，再由 `images_upload_handler` **异步**上传，上传完成后才替换成 `upload/tmp/xxx` 的短地址；而提交是**同步**的 —— 上传没完成就点提交时，正文里还是那坨 base64，长度约为图片字节的 4/3，一旦超过服务端上限（`route/post.php` 的 `mb_strlen($message) > 2048000`）就报「内容太长」（`message_too_long`），等异步上传完成后再点**第二次**才成功。因此**只要粘贴的图片大于约 1.5MB 就必然要点两次**，且第一次要把好几 MB 的正文 POST 出去，表现为"很慢 → 弹窗 → 再点一次成功"
- **修复**：新增提交守卫 `plugin/huux_tinymce/tinymce/upload-guard.js`，由 `hook/post_js.htm` 引入，编辑帖子 / 发帖 / 回帖三个页面同时生效：
  - 用**文档捕获阶段**监听 `submit`，保证早于模板里后绑定的提交处理器（`view/htm/post.htm` 里那段 ajax 提交）执行
  - 提交前先 `editor.save()`，若正文里还有未上传完成的图片（`src` 为 `data:` / `blob:`，或正文长度异常）→ **拦下本次提交**，按钮显示「图片上传中，完成后将自动提交…」，等上传结束（`uploadImages()` + 轮询）后自动重新提交一次
  - 重新提交前会**再 `save()` 一次**：拦截时同步进 textarea 的还是含 base64 的旧内容，不再存一次的话提交出去依旧是大字符串（这个坑在实测中真的踩到了）
  - **超时保护**（约 90 秒）：始终上传不完则提示「有图片还没有上传完成，请稍候再试」并**放行一次**，不会把用户钉死在页面上；没有待上传图片、或没有 TinyMCE 时一律直接放行，不影响原生 textarea 与其它表单
- **实测**（真实 TinyMCE 5.2 + 站点既有配置，构造正文 base64 长度 3,374,019 字符，远超 2048000 上限）：
  - 点击提交后立即检查：提交次数 **0** —— 已拦下，没有把 3.37MB 正文发出去 ✓
  - 上传完成后自动提交 1 次，且提交时正文长度 **55 字符**（短地址）✓，不会再触发长度上限
  - 上传接口仅调用 1 次，没有重复上传 ✓
  - 边界：无图片时直接放行 ✓；上传卡住不回调时超时提示且不擅自提交、手动再点一次可放行 ✓

### v1.8.6 (2026-10-07)

**标签插件（xn_tag）· 修复标签没有外框（"圈"）：**

- **修复前台未选中标签失去边框与底色**：`plugin/xn_tag/hook/header_bootstrap_before.htm` 的 CSS 引用了 `--gray-100 ~ --gray-900`、`--primary-bg-opacity` 这套变量，而 **Bootstrap 4 只定义 `--gray` / `--gray-dark`**（`--gray-100/300/700` 是 Bootstrap 5 / Tailwind 的命名）。CSS 的规则是「变量未定义 → 整条声明被丢弃」，并不是回退到默认值 —— 所以 `border: 1px solid var(--gray-300)` 和 `background: var(--gray-100)` 直接失效：**未选中的标签退化成纯文字（外面那个圈消失）**，`.tag_box-*`（帖子列表 / 详情页的标签）与筛选栏也一起失去配色；只有"已选中"的标签还看得见，因为它用的是 Bootstrap 自带的 `--primary`
- **实测**（headless Chrome 计算值）：修复前 `border-style: none`、`border-width: 0px`、背景透明；修复后 `1px solid #d1d5db` + 圆角 10px + `#f3f4f6` 底色，"选中"为 1px 蓝边 + 蓝底白字

- 这类问题的表现与站点是否装了提供该套变量的主题有关（例如装了轻鸿主题的站点显示正常，没装/没启用的站点就"没有圈"），所以同一份插件在不同站点上长得不一样，和插件数据、文件完整度无关
